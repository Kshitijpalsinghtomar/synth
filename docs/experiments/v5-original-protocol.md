# P6 ESQ-DSL v5 — one-shot external oracle protocol

**Protocol ID:** P6-ESQ-V5-ORACLE-001  
**Date:** 16 November 2026  
**Tracking:** [Issue #21](https://github.com/Kshitijpalsinghtomar/research/issues/21)  
**Baseline commit:** e148240f0b2c0fd8c6ee489df0e3c4474517477b

## Research question

Can a validated one-shot external answer safely resolve ambiguity in the exact-fit candidate portfolio generated by the verified ESQ-DSL v3 search, without wasting oracle calls on invalid queries or losing a usable pre-query candidate after abstention/failure?

## Explicit non-goal: continuous CEGIS

V5 is not a continuous CEGIS loop. A task session is limited to one frozen portfolio, one query selection, zero or one oracle request, and one final selection/fallback. There is no automatic next query, retry after timeout, or post-answer re-synthesis round.

## Invariants

1. V3 exact symbolic enumeration, strict interpreter semantics, and exact execution-signature quotient remain authoritative.
2. V4 learned candidate ranking and V4 CEGIS implementation are not dependencies.
3. Candidate portfolio is frozen before query planning. Candidate order is deterministic; the first candidate is the pre-query fallback.
4. Query planner has no Oracle object/parameter and cannot inspect oracle answers.
5. Query inputs must have the exact task input-variable set and the matching visible-example types.
6. Query values must respect integer/list element bounds, maximum list length, and any supplied input_specs.range / input_specs.length.
7. Every candidate program must execute successfully under the strict v3 interpreter on a proposed input; undefined, invalid, wrong-type, or out-of-bounds predictions reject the entire proposed input.
8. A query is proposed only when the frozen exact-fit candidates disagree on the cached output.
9. Visible examples and reserved fresh-evaluation inputs are excluded from the oracle query pool.
10. Persist query_proposed before the adapter receives the request.
11. At most one Oracle.ask invocation occurs in one task session.
12. A valid answer selects only a frozen candidate whose cached prediction equals the answer exactly.
13. Skip, timeout, malformed/invalid answer, adapter exception, or zero survivors returns the first frozen pre-query candidate. The frozen pool is immutable and preserved.
14. If no safe disagreement query exists, no oracle call is made and the first pre-query candidate is returned.
15. Empty pre-query pools are reported as no-candidate outcomes; fallback is guaranteed when a non-empty pre-query pool exists.

## Formal interface

~~~python
class Oracle(Protocol):
    adapter_name: str
    def ask(self, request: OracleRequest) -> OracleResponse: ...

@dataclass(frozen=True)
class OracleRequest:
    query_id: str
    task_id: str
    inputs: dict[str, Any]
    expected_type: str

@dataclass(frozen=True)
class OracleResponse:
    status: OracleStatus
    value: Any = None
    detail: str | None = None
~~~

Statuses: answered, skipped, timed_out, invalid, error.

### Human adapter

One prompt, one raw response. JSON is parsed once. skip, unknown, or EOF map to skipped; malformed JSON maps to invalid. Type/bounds validation is centralized in the coordinator. No re-prompt.

### Local subprocess adapter

- Command is passed as an argument vector; shell=False.
- One request JSON is written to stdin; one JSON response is read from stdout.
- subprocess.run(..., timeout=...) strictly bounds execution time.
- Non-zero exit, launch error, timeout, malformed response, and oversized output are typed outcomes.
- The child process receives only the task/query IDs, selected input, and expected type, not the candidate portfolio or the hidden target.

## Query selection

For each proposed query-pool row:
1. Canonicalize and deduplicate it.
2. Exclude visible and reserved evaluation inputs.
3. Validate exact variable set, input type, numeric bound, list length and task-specific specifications.
4. Execute every frozen candidate through strict interpreter semantics.
5. Reject the input if any candidate execution is undefined, invalid, wrong type, or out of bounds.
6. Retain only inputs with at least two distinct candidate predictions.

Select the query deterministically by descending number of distinct predictions, descending pairwise disagreement count, then ascending query SHA-256. No oracle or reference target is available to this function.

## Fallback semantics

The frozen candidate sequence is immutable. The default fallback is the first pre-query candidate (v3's visible-only portfolio order). On any non-answer outcome or zero survivors, the coordinator emits fallback_selected and returns that candidate. It never empties or mutates the original candidate pool.

No best-partial candidate may be introduced during this stage; the workflow operates only on the frozen v3 candidate portfolio. When candidate rows are not exact fits, query planning abstains and preserves the first row.

## Provenance

JSONL events are sequenced with UTC timestamps. A file-backed recorder flushes and fsyncs each event. Events include:
- portfolio freeze: candidate IDs/hashes and portfolio hash;
- screening counts and rejection reasons;
- query ID/hash, selected input, query-pool stats, predictions and frozen candidate IDs;
- oracle_requested with adapter identity;
- response status, detail and answer hash (not the raw answer);
- survivor IDs or fallback candidate/reason.

Task data and selected query input are retained for audit; raw answer content is not recorded by default.

## Required tests

- query proposal is logged before adapter access;
- one oracle call maximum per session;
- malformed, wrong-type, out-of-range, wrong-length and task-spec-invalid input rejection;
- candidate strict-execution errors/undefined values/output bounds reject query;
- visible/evaluation input disjointness;
- no disagreement/no safe input means no oracle request;
- valid answer chooses an exact cached-prediction survivor;
- skip, unknown, EOF, malformed answer, invalid answer type, timeout, subprocess error and non-zero exit preserve fallback;
- zero survivors preserves the frozen portfolio and returns fallback;
- provenance event order, hashes, sequence and raw-answer omission;
- real v3 interpreter integration and unchanged v3 regression suite.

## Fresh evaluation protocol

All six ExeDec DeepCoder split cohorts used in the previous P6 v3/v4 work are consumed for the historical comparisons; they are not fresh v5 confirmation data.

The v5 confirmation cohort is generated from a new seed stream with the pinned v3 generator, then excludes any structural family whose SHA-256 appears in the previously used 100k synthetic corpus (which includes all v3 train/development/confirmation families). The runner pins the exact 100k corpus SHA, 100,000 task rows, and 54,649 unique family hashes; it aborts if these checks do not match. It also pins the exact v3 checkpoint SHA. If the requested new-family count cannot be obtained, the run aborts; never relax family disjointness silently.

Before candidate generation, freeze:
- the raw target-bearing cohort digest and hidden-target bundle digest separately;
- the exact visible-only projection and its hash;
- ordered structural family list and family-overlap check;
- task-generator source/version, seed stream and task count;
- v3 checkpoint/code hashes and search settings;
- all query pools and reserved evaluation inputs plus their combined hash.

Candidate portfolios are generated from visible inputs/outputs only, then hash-locked before the subprocess harness receives access to hidden target programs. The harness is allowed to answer only the single proposed input per task. Fresh evaluation inputs are disjoint from visible examples and query pool. After all candidates and portfolios are frozen, score v3 top-1 and v5 one-shot selections on the same held-out fresh evaluation inputs.

Report full fresh-behaviour matches, case accuracy, queryable tasks, no-safe-query abstentions, oracle valid answers, skips/errors/timeouts, invalid-output responses, zero-survivor fallbacks, candidate fallback rate, query screening rejection counts, latency, and unresolved tasks.

A harness reading hidden synthetic reference programs is an external process boundary, but it is still simulated-oracle evaluation. Do not call it an official external ExeDec benchmark or autonomous inference result.

## Claim boundary

A pass establishes software correctness and bounded utility only for the tested DSL, task generator/source, oracle contract and resource limits. It does not establish novelty, state of the art, general-purpose synthesis, or publication readiness.
